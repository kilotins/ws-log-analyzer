Data Flow

  1. Ingest — Upload via web, CLI, or API → store raw log in Object Store
  2. Parse — Rust engine, streaming: raw bytes → structured LogEvent stream
  3. Classify — Enrich each event with level, code, exception, signal tags
  4. Persist — Write structured events to Parquet / ClickHouse
  5. Analyze — Heuristics, cascades, incidents, evidence extraction
  6. Notify — WebSocket push: “analysis ready”
  7. AI Explain — User-triggered: redaction gate → provider → streamed response
  8. Report — Generate PDF/HTML/JSON/Markdown artifacts

Key insight

The API layer is I/O-bound (database, AI calls, file handling) — Python is fine. The CPU-bound work (parsing, classification) starts in Python (V1) and graduates to Rust (V2) when performance demands it. This split means we ship fast and optimize later.

5. Organizations, Workspaces & Auth

Three-layer model

Organization (the customer) → Workspaces (data isolation) → Members (users with roles). On a laptop, all three layers are auto-created and invisible. In SaaS/enterprise, they unlock team structure, billing, and cross-workspace admin.

The Hierarchy

Organization: Acme Corp (billing, IdP config, org-admin) ├── Workspace: DevOps (isolated data, AI settings) │ ├── Anna (admin) │ └── Erik (member) ├── Workspace: SecOps (isolated data, AI settings) │ ├── Erik (viewer) ← same person, different role │ └── Maria (admin) └── Workspace: Developers (isolated data, AI settings) ├── Anna (member) ← same person, different role └── Johan (member)
  • Organization — the paying customer (Acme Corp, Contoso, etc). Owns billing, OIDC/IdP configuration, and org-level admin. In SaaS: one org per customer. Self-hosted: typically one org per installation.
  • Workspace — the data isolation boundary. Each workspace has its own log sessions, analysis results, AI history, and settings. Data never leaks between workspaces — enforced by the database (RLS), not just application code.
  • Member — a user + role in a workspace. A user can be a member of multiple workspaces with different roles (admin in DevOps, viewer in SecOps).

Settings Inheritance

Settings cascade: organization → workspace. Workspace settings override org defaults. This means an org-admin can set a default AI key for the whole organization, but the SecOps workspace can override it with their own key.

# Resolve effective settings for a workspace
def resolve_settings(org: Organization, ws: Workspace) -> EffectiveSettings:
    base = org.settings.copy()         # org defaults
    base.update(ws.settings)           # workspace overrides
    return EffectiveSettings(**base)

# Example:
# org.settings  = {"ai_provider": "claude", "ai_key": "sk-org-..."}
# ws.settings   = {"ai_key": "sk-secops-..."}   ← SecOps uses own key
# effective     = {"ai_provider": "claude", "ai_key": "sk-secops-..."}

Typed Redaction Gate (Non-Bypassable)

Critical security design

AI providers only accept RedactedText, a wrapper type that can only be created by the RedactionGate. It is architecturally impossible to send unredacted data to an external AI provider.

class RedactedText:
    """Newtype wrapper. Cannot be constructed except by RedactionGate."""
    _value: str  # private

    def __init__(self):
        raise TypeError("Use RedactionGate.redact()")

class RedactionGate:
    def redact(self, text: str, ws_config: WorkspaceConfig) -> RedactedText:
        # 1. Standard: tokens, passwords, API keys, emails, IPs
        # 2. Workspace-specific patterns (custom regex from settings)
        # 3. Optional named entity removal
        ...

class AIProvider(Protocol):
    async def complete(
        self,
        system: RedactedText,   # ← cannot pass raw str
        user: RedactedText,     # ← cannot pass raw str
        model: str,
        stream: bool = True,

Knowledge Retrieval (RAG)

Not generic RAG

RAG in LogPilot is not about searching the internet or general documentation. It’s about letting the AI reference the customer’s own history and ops knowledge — previous incidents, runbooks, and internal procedures. The system gets smarter the more it is used.

Three knowledge sources, all opt-in per workspace:

SourceWhat is indexedValue
Previous incidents Incident fingerprints, AI explanations, and resolutions from the same workspace “This matches an incident from Nov 12 — the root cause was DNS failover after a provider outage.”
Runbooks / documentation Confluence pages, wikis, markdown files — ops procedures indexed per workspace “Your runbook says: restart nodeagent first when CWWKZ0002E occurs.”
Source code Vector embeddings of functions and classes (extends source lookup from section 9) “Related code in ConnectionPool.java — the retry logic was changed 3 days ago.”

RAG context is assembled after heuristics and before the redaction gate — it enriches the AI prompt, it does not replace the structured analysis:

Incident detected → Heuristics + Evidence (always) → Source code lookup (if repo connected) → RAG: similar past incidents (if history exists) → RAG: relevant runbook sections (if indexed) → All assembled → RedactionGate → AI → Explanation

Vector Index Strategy

  • Storage: pgvector extension in Postgres — no new database, same adapter pattern. Self-service uses SQLite with a lightweight vector extension.
  • Embedding model: Configurable per workspace. Cloud: OpenAI text-embedding-3-small or similar. Self-service: local model (e.g. all-MiniLM-L6-v2 via sentence-transformers, ~80 MB, runs on CPU).
  • Incremental indexing: Every AI explanation LogPilot produces is automatically embedded and indexed. Previous incidents become searchable knowledge without any manual effort.
  • Search: Cosine similarity on incident fingerprint + text embedding. Top 3 most similar results included in prompt context.
Compound learning

Every incident LogPilot explains becomes knowledge for the next incident. After 6 months of use, the AI doesn’t just analyze logs — it draws on the workspace’s entire incident history. “We’ve seen this pattern 4 times before. Each time the fix was X. The last occurrence was 3 weeks ago.”

Build priority: V2

RAG requires good AI explanations to exist first — they are the content that gets indexed. Ship the core AI pipeline in V1, then add RAG retrieval in V2 once workspaces have accumulated incident history worth searching.

7. Privacy & Data Residency

This is not a feature — it is a core invariant

Sensitive data must never leave the system unredacted. Customer data must never be forced outside their chosen region. These are not configurable options — they are architectural guarantees enforced by the type system and deployment model.

Principle 1: No Raw Data to External AI

The RedactedText newtype (described in section 6) enforces this at the code level. But the principle extends beyond AI:

Data flowWhat happensEnforcement
Log events → AI provider Redacted before sending. Tokens, passwords, API keys, emails, IPs stripped. Custom workspace patterns applied. Type system: AI providers only accept RedactedText
Log events → reports Redacted at parse time. Reports contain only redacted text. redact() runs during parsing, before events enter the system
Log events → database Stored post-redaction. Raw log content is in object store only. Parse pipeline: redaction is step 2, before persist
AI prompts → audit log Prompt hash stored, not prompt text. For debugging without storing PII. Audit table schema: redacted_prompt_hash, not prompt_text

What Gets Redacted

Authentication tokensBearer tokens, JWT, session cookies, API keysPattern replacement: [REDACTED_TOKEN]
PasswordsPassword fields in URLs, config lines, log messagesPattern replacement: [REDACTED_PASSWORD]
Personal identifiersEmail addresses, phone numbers, national IDs (SSN, fødselsnummer)Pattern replacement: [REDACTED_EMAIL], [REDACTED_ID]
Network identifiersIP addresses (optional, configurable per workspace)Configurable: redact, anonymize (hash), or keep

Principle 2: Data Stays Where the Customer Chooses

DeploymentWhere data livesWhat leaves the system
Laptop (self-service) Local disk only (~/.logpilot/) Nothing — unless user explicitly enables external AI. Then: only redacted prompts to chosen provider.
Team server (self-service) Customer’s own Postgres + filesystem/S3 Only redacted AI prompts, only if external AI is enabled.
Customer cloud (self-service) Customer’s own cloud account (EU, Norway, anywhere) Only redacted AI prompts. Customer controls which AI provider and region.
SaaS (we host) Our infrastructure — EU region (Norway/EU data center) Only redacted AI prompts to customer’s chosen AI provider.

SaaS Data Residency

  • Default SaaS region: EU (Norway or EU data center). Not US. This is a deliberate market positioning choice for Nordic/European customers.
  • All customer data (logs, events, analysis results, AI conversations) stays in the chosen region.
  • AI providers are configurable per workspace. Customer can choose EU-hosted AI endpoints, or disable external AI entirely and use local models only.
  • No telemetry or usage data leaves the region without explicit opt-in.

8. Data Processing Strategy

The Problem

A 10 GB log file contains ~50M lines, ~10M events. Loading everything into a Python list = OOM.

Solution: Streaming Pipeline with Materialized Checkpoints

StageEngineInputOutputMemory
1. Parse Rust, streaming Raw file (mmap) Events in 100K-row Parquet batches ~Constant
2. Classify Rust, batch parallel Parquet batches Enriched Parquet (added columns) ~Batch size
3. Index Rust Enriched Parquet Time-series index + inverted index Small (fits in RAM)
4. Analyze Python Index artifacts (not raw events!) Heuristic matches, incidents Small
5. AI Python, on-demand Analysis results (not raw events) Explanation, streamed to user Prompt size
Key insight

After Stage 3, most operations work on indexes and aggregates, not raw events. The heuristic engine needs “how many events match pattern X?” and “give me 5 examples” (a targeted Parquet scan) — not 10M events in memory.

Why Parquet as the Intermediate Format

  • Columnar: Reading only ts_utc + level for a histogram doesn’t load text (90% of the data)
  • Compressed: Repetitive log text compresses 10–20x with ZSTD
  • Memory-mappable: DuckDB queries Parquet without full loading
  • Portable: Same format for local (DuckDB) and SaaS (ClickHouse ingests Parquet)

10. Future: Source Code Lookup

This is NOT Sentry

LogPilot does not instrument your application. No SDK, no agent, no runtime access. Instead, when LogPilot finds a stacktrace in your logs, it can optionally look up the corresponding source code in a connected Git repo — giving the AI more context to explain the bug. This is a post-hoc investigation tool, not real-time error tracking.

The Idea

LogPilot already extracts exceptions and stacktraces from logs. Today, the AI explains them based on the log context alone. With an optional Git repo connection, LogPilot can also show which code the stacktrace points to — enriching the investigation without requiring any changes to the customer’s application.

What LogPilot already does What source lookup adds (optional) ┌─────────────────────────┐ ┌────────────────────────────────┐ │ Parses logs │ │ Resolves stacktrace frames │ │ Detects incidents │ + │ to actual source files + lines │ │ Finds root causes │ │ Shows surrounding code │ │ AI explains from log data │ │ AI explains from log + code │ └─────────────────────────┘ └────────────────────────────────┘ works without repo requires optional repo connection

How It Works

  1. Workspace admin connects a repo (optional, one-time). Read-only access via GitHub App, deploy key, PAT, or local path.
  2. LogPilot indexes symbols in the background: builds a lookup table of package.class.method → file:line. This is a lightweight symbol table, not a full copy of the code.
  3. When a stacktrace appears in an incident, LogPilot resolves frames against the symbol table: com.enonic.xp.repo.BlobStore.get() → src/repo/BlobStore.java:142.
  4. The AI context builder includes the resolved source lines (20 lines around the frame) alongside the existing incident data. The AI can now explain the bug in terms of actual code.

The product works fully without a repo connection. Source lookup is a “plug in your repo for deeper insights” feature, not a requirement.

Architecture (Lightweight)

ComponentWhat it does
Git connector Read-only shallow clone or local path mount. Fetches incrementally (on webhook or schedule). Never writes to the repo.
Symbol indexer Parses source files, builds class.method → file:line lookup. Stored in Postgres per workspace. Small: ~1MB per 100K LOC repo.
Frame resolver Maps stacktrace frames from log events to source locations using the symbol index. Fast in-memory lookup.
Context enricher Reads ~20 lines of source around resolved locations. Adds git blame (who, when). Feeds into existing AI context builder.

Security

  • Read-only: LogPilot never writes to the repo. No push access, no PRs, no modifications.
  • Workspace-scoped: Repo connection and symbol index belong to the workspace. RLS applies. Other workspaces cannot see the code.
  • Redaction applies: Source code sent to AI passes through the same RedactionGate. Hardcoded secrets in code are redacted.
  • Minimal data: LogPilot stores a symbol index (~1MB), not a full code copy. Source lines are fetched on-demand for resolved frames only.
Build priority: V2+

The core product — log parsing, heuristics, incident detection, AI explanation — must work excellently without any repo connection. Source lookup is an enrichment layer that makes the AI smarter when available. Architecturally, it is a new adapter (Git connector) and an additional input to the existing AI context builder — no changes to the core analysis pipeline.
