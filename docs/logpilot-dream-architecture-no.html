Dataflyt

  1. Inntak — Last opp via web, CLI, eller API → lagre rålogg i Object Store
  2. Parsing — Rust-motor, strømmende: rå bytes → strukturert LogEvent-strøm
  3. Klassifisering — Berik hver hendelse med nivå, kode, unntak, signaltagger
  4. Lagring — Skriv strukturerte hendelser til Parquet / ClickHouse
  5. Analyse — Heuristikk, kaskader, hendelser, evidensutvinning
  6. Varsling — WebSocket-push: “analyse klar”
  7. AI-forklaring — Brukerinitialisert: redigeringsport → leverandør → strømsvar
  8. Rapport — Generer PDF/HTML/JSON/Markdown-artefakter

Faselegend

V1 = bygges fra dag én. V2 = legges til etter første betalende kunder. Skalering = legges til når spesifikke skalerkrav gjør det nødvendig. Arkitekturen støtter alle komponenter, men de bygges i rekkefølge etter kundeverdi.

Nøkkelinnsikt

API-laget er I/O-bundet (database, AI-kall, filhåndtering) — Python holder. CPU-bundet arbeid (parsing, klassifisering) starter i Python (V1) og flyttes til Rust (V2) når ytelsen krever det. Dette skillet betyr at vi sender raskt og optimaliserer senere.

4. Én kodebase — Adapter-mønster

Alle infrastrukturanliggender har et Python Protocol med nøyaktig to implementasjoner: én enkel (lokal), én produksjon (SaaS). Funksjonskode berører aldri infrastruktur direkte.

Prosjektstruktur

logpilot/
├── core/           # Parsing, heuristikk, analyse — 100% delt
├── api/            # FastAPI-ruter — 100% delt
├── adapters/       # Infrastrukturabstraksjoner
│   ├── storage/    #   S3Store, LocalStore
│   ├── database/   #   PostgresDB, SQLiteDB
│   ├── events/     #   ClickHouseEvents, DuckDBEvents
│   ├── queue/      #   RedisQueue, InlineQueue
│   ├── cache/      #   RedisCache, MemoryCache
│   └── auth/       #   OIDCAuth, LocalAuth, NoAuth
├── ai/             # Redigering, leverandører, prompts — 100% delt
├── workers/        # Bakgrunnsjobber — 100% delt
└── frontend/       # React-app — 100% delt

5. Organisasjoner, arbeidsområder & autentisering

Trelags modell

Organisasjon (kunden) → Arbeidsområder (dataisolasjon) → Medlemmer (brukere med roller). På en laptop opprettes alle tre lagene automatisk og er usynlige. I SaaS/bedrift låser de opp teamstruktur, fakturering og administrasjon på tvers av arbeidsområder.

Hierarkiet

Organization: Acme Corp (billing, IdP config, org-admin) ├── Workspace: DevOps (isolated data, AI settings) │ ├── Anna (admin) │ └── Erik (member) ├── Workspace: SecOps (isolated data, AI settings) │ ├── Erik (viewer) ← same person, different role │ └── Maria (admin) └── Workspace: Developers (isolated data, AI settings) ├── Anna (member) ← same person, different role └── Johan (member)
  • Organisasjon — den betalende kunden (Acme Corp, Contoso osv.). Eier fakturering, OIDC/IdP-konfigurasjon og administrasjon på organisasjonsnivå. I SaaS: én org per kunde. Selvdriftet: typisk én org per installasjon.
  • Arbeidsområde — dataisolasjonsgrensen. Hvert arbeidsområde har egne loggøkter, analyseresultater, AI-historikk og innstillinger. Data lekker aldri mellom arbeidsområder — håndhevet av databasen (RLS), ikke bare applikasjonskode.
  • Medlem — en bruker + rolle i et arbeidsområde. En bruker kan være medlem av flere arbeidsområder med forskjellige roller (admin i DevOps, viewer i SecOps).

Datamodell (konseptuell)

Dette er skjemaet på designnivå som viser trelags hierarkiet. For den fullstendige produksjons-DDL med alle tabeller, indekser og RLS-policyer, se Prosjektplanen — Databaseskjema.

Laptop: Usynlig stillasbygging

På en laptop eksisterer trelags-modellen fremdeles i databasen — men brukeren ser den aldri. Alt opprettes automatisk ved første oppstart:

# Første-oppstart-logikk — laptop-modus krever null brukerinteraksjon
async def ensure_local_setup(db: Database):
    """Kalles ved oppstart når auth_backend == 'none'.
    Oppretter automatisk org + arbeidsområde + bruker. Brukeren går rett til arbeid."""
    if await db.has_any_org():
        return
    org = await db.create_org(name="Local", slug="local")
    ws = await db.create_workspace(org.id, name="Personal", slug="personal")
    user = await db.create_user(email="local@logpilot", name="Local User")
    await db.add_org_member(org.id, user.id, role="org_admin")
    await db.add_ws_member(ws.id, user.id, role="admin")
    # Bruker åpner appen → allerede innlogget → allerede i "Personlig" arbeidsområde
    # Ingen innloggingsskjerm, ingen org-velger, ingen arbeidsområdevalg. Bare appen.
Dagen du vokser

Når en laptop-bruker senere kobler seg til en teamserver eller oppgraderer til SaaS, er strukturen allerede på plass. Aktiver autentisering, opprett flere arbeidsområder, inviter lagkamerater. Ingen migrering, ingen skjemaendring — bare konfigurasjon.

Innstillingsarv

Innstillinger kaskaderer: organisasjon → arbeidsområde. Arbeidsområdeinnstillinger overstyrer org-standarder. Dette betyr at en org-admin kan sette en standard AI-nøkkel for hele organisasjonen, men SecOps-arbeidsområdet kan overstyre det med sin egen nøkkel.

# Løs effektive innstillinger for et arbeidsområde
def resolve_settings(org: Organization, ws: Workspace) -> EffectiveSettings:
    base = org.settings.copy()         # org-standarder
    base.update(ws.settings)           # arbeidsområde overstyrer
    return EffectiveSettings(**base)

# org.settings  = {"ai_provider": "claude", "ai_key": "sk-org-..."}
# ws.settings   = {"ai_key": "sk-secops-..."}   ← SecOps bruker egen nøkkel
# effective     = {"ai_provider": "claude", "ai_key": "sk-secops-..."}

Typet redigeringsport (ikke-omgåelig)

Kritisk sikkerhetsdesign

AI-leverandører aksepterer kun RedactedText, en wrapper-type som kun kan opprettes av RedactionGate. Det er arkitektonisk umulig å sende uredigert data til en ekstern AI-leverandør.

    """Newtype wrapper. Cannot be constructed except by RedactionGate."""
    _value: str  # private

    def __init__(self):
        raise TypeError("Use RedactionGate.redact()")

class RedactionGate:
    def redact(self, text: str, ws_config: WorkspaceConfig) -> RedactedText:
        # 1. Standard: tokens, passord, API-nøkler, e-poster, IP-er
        # 2. Arbeidsområde-spesifikke mønstre (egendefinert regex fra innstillinger)
        # 3. Valgfri fjerning av navngitte entiteter
        ...

class AIProvider(Protocol):

Kunnskapsinnhenting (RAG)

Ikke generisk RAG

RAG i LogPilot handler ikke om å søke på internett eller generell dokumentasjon. Det handler om å la AI referere kundens egen historikk og driftskunnskaper — tidligere hendelser, kjørebøker og interne prosedyrer. Systemet blir smartere jo mer det brukes.

Tre kunnskapskilder, alle valgfrie per arbeidsområde:

KildeHva indekseresVerdi
Tidligere hendelser Hendelsesfingeravtrykk, AI-forklaringer og løsninger fra samme arbeidsområde “Dette samsvarer med en hendelse fra 12. nov — rotårsaken var DNS-failover etter et leverandøravbrudd.”
Kjørebøker / dokumentasjon Confluence-sider, wikier, markdown-filer — driftsprosedyrer indeksert per arbeidsområde “Kjøreboken din sier: start nodeagent på nytt først når CWWKZ0002E oppstår.”
Kildekode Vektorembeddings av funksjoner og klasser (utvider kildekodeoppslag fra seksjon 9) “Relatert kode i ConnectionPool.java — retry-logikken ble endret for 3 dager siden.”

RAG-kontekst settes sammen etter heuristikk og før redigeringsporten — den beriker AI-prompten, den erstatter ikke den strukturerte analysen:

Incident detected → Heuristics + Evidence (always) → Source code lookup (if repo connected) → RAG: similar past incidents (if history exists) → RAG: relevant runbook sections (if indexed) → All assembled → RedactionGate → AI → Explanation

Vektorindeksstrategi

  • Lagring: pgvector-utvidelse i Postgres — ingen ny database, samme adaptermønster. Selvbetjening bruker SQLite med en lettvekts vektorutvidelse.
  • Embedding-modell: Konfigurerbar per arbeidsområde. Sky: OpenAI text-embedding-3-small eller tilsvarende. Selvbetjening: lokal modell (f.eks. all-MiniLM-L6-v2 via sentence-transformers, ~80 MB, kjører på CPU).
  • Inkrementell indeksering: Hver AI-forklaring LogPilot produserer embeddes automatisk og indekseres. Tidligere hendelser blir søkbar kunnskap uten manuell innsats.
  • Søk: Cosinus-likhet på hendelsesfingeravtrykk + tekstembedding. Topp 3 mest like resultater inkluderes i promptkonteksten.
Sammensatt læring

Hver hendelse LogPilot forklarer blir kunnskap for neste hendelse. Etter 6 måneders bruk analyserer ikke AI bare logger — den trekker på arbeidsområdets hele hendelseshistorikk. “Vi har sett dette mønsteret 4 ganger tidligere. Hver gang var løsningen X. Siste forekomst var for 3 uker siden.”

Byggeprioritet: V2

RAG krever gode AI-forklaringer først — de er innholdet som indekseres. Send kjernen av AI-pipelinen i V1, legg deretter til RAG-henting i V2 når arbeidsområder har akkumulert hendelseshistorikk verdt å søke i.

8. Dataprosesseringsstrategi

Problemet

En 10 GB loggfil inneholder ~50M linjer, ~10M hendelser. Å laste alt inn i en Python-liste = OOM.

Løsning: Strømmende pipeline med materialiserte sjekkpunkter

StegMotorInnUtMinne
1. Parse Rust, strømmende Råfil (mmap) Hendelser i 100K-raders Parquet-pakker ~Konstant
2. Klassifiser Rust, parallell batch Parquet-pakker Beriket Parquet (ekstra kolonner) ~Pakkestørrelse
3. Indekser Rust Beriket Parquet Tidsserieindeks + invertert indeks Liten (får plass i RAM)
4. Analyser Python Indeksartefakter (ikke råhendelser!) Heuristikk-treff, hendelser Liten
5. AI Python, på forespørsel Analyseresultater (ikke råhendelser) Forklaring, strømmet til bruker Promptstørrelse
Nøkkelinnsikt

Etter steg 3 arbeider de fleste operasjoner på indekser og aggregater, ikke råhendelser. Heuristikkmotoren trenger “hvor mange hendelser samsvarer med mønster X?” og “gi meg 5 eksempler” (et målrettet Parquet-søk) — ikke 10M hendelser i minnet.

Hvorfor Parquet som mellomformat

  • Kolumnebasert: Å lese kun ts_utc + level for et histogram laster ikke inn text (90 % av dataene)
  • Komprimert: Repetitiv loggtekst komprimeres 10–20x med ZSTD
  • Minnekartleggbar: DuckDB spørringer mot Parquet uten full innlasting
  • Portabelt: Samme format for lokalt (DuckDB) og SaaS (ClickHouse importerer Parquet)

async def get_current_user(request: Request) -> AuthUser:

# Structured: send JSON log events directly
curl -X POST https://logpilot.io/api/v1/ingest \

  -d '{"ts":"2026-03-20T10:15:00Z","level":"ERROR","msg":"Connection refused","source":"enonic-prod"}'

10. Fremtidig: Kildekodeoppslag

Dette er IKKE Sentry

LogPilot instrumenterer ikke applikasjonen din. Ingen SDK, ingen agent, ingen runtime-tilgang. I stedet kan LogPilot, når det finner en stacktrace i loggene dine, valgfritt slå opp tilsvarende kildekode i et tilkoblet Git-repo — noe som gir AI mer kontekst for å forklare feilen. Dette er et etterforskningsverktøy i etterkant, ikke sanntids feilsporing.

Ideen

LogPilot henter allerede ut unntak og stacktraces fra logger. I dag forklarer AI dem basert på loggkonteksten alene. Med en valgfri Git-repo-tilkobling kan LogPilot også vise hvilken kode stacktracen peker på — noe som beriker undersøkelsen uten at kunden trenger å endre applikasjonen sin.

What LogPilot already does What source lookup adds (optional) ┌─────────────────────────┐ ┌────────────────────────────────┐ │ Parses logs │ │ Resolves stacktrace frames │ │ Detects incidents │ + │ to actual source files + lines │ │ Finds root causes │ │ Shows surrounding code │ │ AI explains from log data │ │ AI explains from log + code │ └─────────────────────────┘ └────────────────────────────────┘ works without repo requires optional repo connection

Slik fungerer det

  1. Workspace-admin kobler til et repo (valgfritt, én gang). Lesetilgang via GitHub App, deploy-nøkkel, PAT eller lokal sti.
  2. LogPilot indekserer symboler i bakgrunnen: bygger en oppslagstabell over pakke.klasse.metode → fil:linje. Dette er en lettvekts symboltabell, ikke en full kopi av koden.
  3. Når en stacktrace dukker opp i en hendelse, løser LogPilot opp rammer mot symboltabellen: com.enonic.xp.repo.BlobStore.get() → src/repo/BlobStore.java:142.
  4. AI-kontekstbyggeren inkluderer de oppløste kildelinjene (20 linjer rundt rammen) ved siden av de eksisterende hendelsesdataene. AI kan nå forklare feilen i form av faktisk kode.

Hva brukeren ser

Uten kildekodeoppslag (standard)Med kildekodeoppslag (repo tilkoblet)
Hendelse: Database Connection Cascade
Årsak: NullPointerException i BlobStore.get()
Bevis: 47 forekomster, 3 systemer berørt
AI sier: “Blob store-oppslaget feiler når cache-nøkkelen er null, sannsynligvis under en indeksoppbygging...” 		Hendelse: Database Connection Cascade
Årsak: NullPointerException i BlobStore.get()
Kilde: src/repo/BlobStore.java:142
Kode: blob = cache.get(key);
Sist endret: 15. feb av dev@enonic.com
AI sier: “Linje 142 sender key til cache.get() uten null-sjekk. key blir null når RepoIndex.rebuild() (linje 89) kjører under en cluster-splittelse. Fix: legg til if (key == null) return Optional.empty(); før cache-oppslaget.”

Produktet fungerer fullt ut uten repo-tilkobling. Kildekodeoppslag er en “koble til repo for dypere innsikt”-funksjon, ikke et krav.

Arkitektur (lettvekts)

KomponentHva det gjør
Git-kobling Lesetilgang, grunne kloner eller lokal stikoppling. Henter inkrementelt (via webhook eller tidsplan). Skriver aldri til repoen.
Symbolindekserer Parser kildefiler, bygger klasse.metode → fil:linje-oppslag. Lagret i Postgres per workspace. Lite: ~1 MB per 100K LOC repo.
Rammeløser Kobler stacktrace-rammer fra logghendeliser til kildelokasjoner ved hjelp av symbolindeksen. Rask oppslag i minnet.
Kontekstberiker Leser ~20 linjer kildekode rundt oppløste lokasjoner. Legger til git blame (hvem, når). Mates inn i eksisterende AI-kontekstbygger.

Tilkoblingsalternativer

MetodeBest for
GitHub AppSaaS-kunder på GitHub — én-klikks installasjon
GitLab OAuth / prosjekttokenGitLab-brukere
Deploy-nøkkel (SSH, skrivebeskyttet)Alle Git-verter, selvdriftet Git
Lokal stiSelf-service på bærbar PC — pek bare til repomappen din, ingen nettverktilgang nødvendig

Språkstøtte

SpråkSlik fungerer stacktrace → kilde
Java / KotlinPakkesti maps deterministisk til filsti. Beste støtte.
PythonTracebacks inkluderer filsti og linjenummer direkte.
JavaScript / TypeScriptNode.js-traces inkluderer stier. Buntet nettleserkode trenger source maps.
GoPanic-traces inkluderer fil:linje.

Sikkerhet

  • Skrivebeskyttet: LogPilot skriver aldri til repoen. Ingen push-tilgang, ingen pull requests, ingen endringer.
  • Workspace-avgrenset: Repo-tilkobling og symbolindeks tilhører workspace-et. RLS gjelder. Andre workspaces kan ikke se koden.
  • Redaksjon gjelder: Kildekode sendt til AI passerer gjennom samme RedactionGate. Hardkodede hemmeligheter i kode redigeres.
  • Minimale data: LogPilot lagrer en symbolindeks (~1 MB), ikke en fullstendig kodekopi. Kildelinjer hentes on-demand kun for oppløste rammer.
Byggeprioritet: V2+

Kjerneprodukte — loggparsing, heuristikk, hendelsesdeteksjon, AI-forklaring — må fungere utmerket uten noen repo-tilkobling. Kildekodeoppslag er et berikingslag som gjør AI smartere når det er tilgjengelig. Arkitektonisk er det en ny adapter (Git-kobling) og ett ekstra inndata til den eksisterende AI-kontekstbyggeren — ingen endringer i kjerneanalysepipelinen.
