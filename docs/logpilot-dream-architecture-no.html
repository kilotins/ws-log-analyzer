Dataflyt

  1. Innlasting — Last opp via web, CLI, eller API → lagre rålogg i objektlageret
  2. Parsing — Rust-motor, strømmende: råbytes → strukturert LogEvent-strøm
  3. Klassifisering — Berik hver hendelse med nivå, kode, unntak, signal-tagger
  4. Lagring — Skriv strukturerte hendelser til Parquet / ClickHouse
  5. Analyse — Heuristikk, kaskader, hendelser, bevisutvinning
  6. Varsling — WebSocket-push: “analyse klar”
  7. AI-forklaring — Brukerstartet: redaksjonsport → tilbyder → strømmet svar
  8. Rapport — Generer PDF/HTML/JSON/Markdown-artefakter

Fasebetegnelser

V1 = bygges fra dag én. V2 = legges til etter de første betalende kundene. Skala = legges til når spesifikke skalingskrav krever det. Arkitekturen støtter alle komponenter, men de bygges i rekkefølge etter kundeverdi.

Viktig innsikt

API-laget er I/O-begrenset (database, AI-kall, filhåndtering) — Python fungerer fint. Det CPU-intensive arbeidet (parsing, klassifisering) starter i Python (V1) og oppgraderes til Rust (V2) når ytelseskravene krever det. Denne delingen betyr at vi leverer raskt og optimaliserer senere.

4. Én kodebase — adaptermønster

Ethvert infrastrukturanliggende har et Python Protocol med nøyaktig to implementasjoner: én enkel (lokal), én produksjon (SaaS). Funksjonskoden berører aldri infrastruktur direkte.

Prosjektstruktur

logpilot/
├── core/           # Parsing, heuristics, analysis — 100% shared
├── api/            # FastAPI routes — 100% shared
├── adapters/       # Infrastructure abstractions
│   ├── storage/    #   S3Store, LocalStore
│   ├── database/   #   PostgresDB, SQLiteDB
│   ├── events/     #   ClickHouseEvents, DuckDBEvents
│   ├── queue/      #   RedisQueue, InlineQueue
│   ├── cache/      #   RedisCache, MemoryCache
│   └── auth/       #   OIDCAuth, LocalAuth, NoAuth
├── ai/             # Redaction, providers, prompts — 100% shared
├── workers/        # Background jobs — 100% shared
└── frontend/       # React app — 100% shared

Adaptorgrensesnitt

    async def list_keys(self, prefix: str) -> list[str]: ...

# adapters/queue/base.py
class JobQueue(Protocol):

5. Organisasjoner, arbeidsområder og autentisering

Tre-lagsmodell

Organisasjon (kunden) → Arbeidsområder (dataisolasjon) → Medlemmer (brukere med roller). På en laptop opprettes alle tre lagene automatisk og er usynlige. I SaaS/bedrift låser de opp teamstruktur, fakturering og administrasjon på tvers av arbeidsområder.

Hierarkiet

Organization: Acme Corp (billing, IdP config, org-admin) ├── Workspace: DevOps (isolated data, AI settings) │ ├── Anna (admin) │ └── Erik (member) ├── Workspace: SecOps (isolated data, AI settings) │ ├── Erik (viewer) ← same person, different role │ └── Maria (admin) └── Workspace: Developers (isolated data, AI settings) ├── Anna (member) ← same person, different role └── Johan (member)
  • Organisasjon — den betalende kunden (Acme Corp, Contoso, osv.). Eier fakturering, OIDC/IdP-konfigurasjon og administrasjon på organisasjonsnivå. I SaaS: én org per kunde. Selvdriftet: typisk én org per installasjon.
  • Arbeidsområde — grensen for dataisolasjon. Hvert arbeidsområde har sine egne loggøkter, analyseresultater, AI-historikk og innstillinger. Data lekker aldri mellom arbeidsområder — håndhevet av databasen (RLS), ikke bare applikasjonskode.
  • Medlem — en bruker + rolle i et arbeidsområde. En bruker kan være medlem i flere arbeidsområder med forskjellige roller (admin i DevOps, visningsgast i SecOps).

Datamodell (konseptuell)

Dette er skjemaet på designnivå som viser tre-lagshierarkiet. For fullstendig produksjons-DDL med alle tabeller, indekser og RLS-policyer, se Prosjektplan — Databaseskjema.

-- Layer 1: Organization (the customer)
CREATE TABLE organizations (
    id          uuid PRIMARY KEY,
    name        text NOT NULL,
    slug        text UNIQUE NOT NULL,    -- URL: app.logpilot.io/klp/...
    plan        text DEFAULT 'free',     -- free | pro | enterprise (SaaS billing)
    settings    jsonb DEFAULT '{}',     -- OIDC config, default AI keys, retention
    created_at  timestamptz DEFAULT NOW()
);

-- Layer 2: Workspaces (data isolation)
CREATE TABLE workspaces (
    id          uuid PRIMARY KEY,
    org_id      uuid REFERENCES organizations NOT NULL,
    name        text NOT NULL,
    slug        text NOT NULL,            -- URL: app.logpilot.io/klp/devops/...
    settings    jsonb DEFAULT '{}',     -- overrides org defaults (AI keys, limits)
    created_at  timestamptz DEFAULT NOW(),
    UNIQUE(org_id, slug)
);

-- Users (global, can belong to multiple orgs/workspaces)
CREATE TABLE users (
    id              uuid PRIMARY KEY,
    email           text UNIQUE NOT NULL,
    name            text,
    auth_provider   text,               -- "google", "azure_ad", "local", "none"
    auth_subject    text,               -- external IdP subject ID
    created_at      timestamptz DEFAULT NOW()
);

-- Org membership (org-level role: org-admin can manage all workspaces)
CREATE TABLE org_memberships (
    org_id       uuid REFERENCES organizations,
    user_id      uuid REFERENCES users,
    role         text NOT NULL,           -- org_admin | member
    PRIMARY KEY (org_id, user_id)
);

-- Layer 3: Workspace membership (per-workspace role)
CREATE TABLE workspace_memberships (
    workspace_id uuid REFERENCES workspaces,
    user_id      uuid REFERENCES users,
    role         text NOT NULL,           -- admin | member | viewer
    PRIMARY KEY (workspace_id, user_id)
);

-- All data is scoped to a workspace
CREATE TABLE sessions (
    id            uuid PRIMARY KEY,
    workspace_id  uuid REFERENCES workspaces NOT NULL,
    name          text,
    created_by    uuid REFERENCES users,
    created_at    timestamptz DEFAULT NOW()
);

Laptop: usynlig stillasbygging

På en laptop eksisterer tre-lagsmodellen fortsatt i databasen — men brukeren ser den aldri. Alt opprettes automatisk ved første oppstart:

# First-start logic — laptop mode needs zero user interaction
async def ensure_local_setup(db: Database):
    """Called at startup when auth_backend == 'none'.
    Auto-creates org + workspace + user. User goes straight to work."""
    if await db.has_any_org():
        return
    org = await db.create_org(name="Local", slug="local")
    ws = await db.create_workspace(org.id, name="Personal", slug="personal")
    user = await db.create_user(email="local@logpilot", name="Local User")
    await db.add_org_member(org.id, user.id, role="org_admin")
    await db.add_ws_member(ws.id, user.id, role="admin")
    # User opens the app → already logged in → already in "Personal" workspace
    # No login screen, no org picker, no workspace selector. Just the app.
Dagen du vokser

Når en laptopbruker senere kobler seg til en teamserver eller oppgraderer til SaaS, er strukturen allerede på plass. Aktiver autentisering, opprett flere arbeidsområder, inviter teammedlemmer. Ingen migrering, ingen skjemaendring — bare konfigurasjon.

Arv av innstillinger

Innstillinger kaskaderer: organisasjon → arbeidsområde. Arbeidsområdeinnstillinger overstyrer org-standarder. Dette betyr at en org-admin kan angi en standard AI-nøkkel for hele organisasjonen, men SecOps-arbeidsområdet kan overstyre den med sin egen nøkkel.

# Resolve effective settings for a workspace
def resolve_settings(org: Organization, ws: Workspace) -> EffectiveSettings:
    base = org.settings.copy()         # org defaults
    base.update(ws.settings)           # workspace overrides
    return EffectiveSettings(**base)

# Example:
# org.settings  = {"ai_provider": "claude", "ai_key": "sk-org-..."}
# ws.settings   = {"ai_key": "sk-secops-..."}   ← SecOps uses own key
# effective     = {"ai_provider": "claude", "ai_key": "sk-secops-..."}

Kunnskapsinnhenting (RAG)

Ikke generisk RAG

RAG i LogPilot handler ikke om å søke på internett eller i generell dokumentasjon. Det handler om å la AI referere til kundens egen historikk og driftskunnskaper — tidligere hendelser, runbooks og interne prosedyrer. Systemet blir smartere jo mer det brukes.

Tre kunnskapskilder, alle valgfrie per workspace:

KildeHva som indekseresVerdi
Tidligere hendelser Hendelsesfingeravtrykk, AI-forklaringer og løsninger fra samme workspace “Dette samsvarer med en hendelse fra 12. nov — rotårsaken var DNS-failover etter et leverandørutfall.”
Runbooks / dokumentasjon Confluence-sider, wikier, markdown-filer — driftsprosedyrer indeksert per workspace “Runbooken din sier: start nodeagent på nytt først når CWWKZ0002E inntreffer.”
Kildekode Vektorembeddings av funksjoner og klasser (utvider kildekodeoppslag fra seksjon 9) “Relatert kode i ConnectionPool.java — retry-logikken ble endret for 3 dager siden.”

RAG-kontekst settes sammen etter heuristikk og før redigeringsporten — den beriker AI-prompten, den erstatter ikke den strukturerte analysen:

Incident detected → Heuristics + Evidence (always) → Source code lookup (if repo connected) → RAG: similar past incidents (if history exists) → RAG: relevant runbook sections (if indexed) → All assembled → RedactionGate → AI → Explanation

Vektorindeksstrategi

  • Lagring: pgvector-utvidelse i Postgres — ingen ny database, samme adaptermønster. Selvbetjening bruker SQLite med en lettvekts vektorutvidelse.
  • Embeddingmodell: Konfigurerbar per workspace. Sky: OpenAI text-embedding-3-small eller tilsvarende. Selvbetjening: lokal modell (f.eks. all-MiniLM-L6-v2 via sentence-transformers, ~80 MB, kjører på CPU).
  • Inkrementell indeksering: Hver AI-forklaring LogPilot produserer blir automatisk embeddet og indeksert. Tidligere hendelser blir søkbar kunnskap uten noe manuelt arbeid.
  • Søk: Cosinuslikhet på hendelsesfingeravtrykk + tekstembedding. De 3 mest lignende resultatene inkluderes i promptkonteksten.
Sammensatt læring

Hver hendelse LogPilot forklarer blir kunnskap for neste hendelse. Etter 6 måneders bruk analyserer ikke AI bare logger — den trekker på workspacets hele hendelseshistorikk. “Vi har sett dette mønsteret 4 ganger tidligere. Hver gang var løsningen X. Siste forekomst var for 3 uker siden.”

Byggeprioritet: V2

RAG krever at gode AI-forklaringer finnes først — de er innholdet som indekseres. Lever kjerne-AI-pipelinen i V1, legg deretter til RAG-innhenting i V2 når workspaces har akkumulert hendelseshistorikk det er verdt å søke i.

7. Personvern & Dataplassering

Dette er ikke en funksjon — det er en kjerneforutsetning

Sensitive data må aldri forlate systemet uredaksivert. Kundedata må aldri tvinges utenfor deres valgte region. Dette er ikke konfigurerbare valg — det er arkitekturelle garantier håndhevet av typesystemet og distribusjonsmodellen.

Prinsipp 1: Ingen rå data til ekstern AI

8. Databehandlingsstrategi

Problemet

En 10 GB loggfil inneholder ~50 millioner linjer, ~10 millioner hendelser. Å laste alt inn i en Python-liste = OOM.

Løsning: Strømmende pipeline med materialiserte kontrollpunkter

StegMotorInputOutputMinne
1. Parse Rust, strømmende Råfil (mmap) Hendelser i 100K-raders Parquet-batches ~Konstant
2. Klassifiser Rust, batch-parallell Parquet-batches Beriket Parquet (tillagte kolonner) ~Batchstørrelse
3. Indekser Rust Beriket Parquet Tidsserieindeks + invertert indeks Liten (passer i RAM)
4. Analyser Python Indeksartefakter (ikke råhendelser!) Heuristiske treff, hendelser Liten
5. AI Python, på forespørsel Analyseresultater (ikke råhendelser) Forklaring, strømmet til bruker Promptstørrelse
Nøkkelinnsikt

Etter steg 3 arbeider de fleste operasjoner på indekser og aggregater, ikke råhendelser. Heuristikkmotoren trenger “hvor mange hendelser matcher mønster X?” og “gi meg 5 eksempler” (et målrettet Parquet-søk) — ikke 10 millioner hendelser i minnet.

Hvorfor Parquet som mellomformat

  • Kolonnebasert: Å lese kun ts_utc + level for et histogram laster ikke text (90 % av dataene)
  • Komprimert: Repetitiv loggtekst komprimeres 10–20x med ZSTD
  • Minneavbildbar: DuckDB spør Parquet uten full innlasting
  • Portabelt: Samme format for lokal (DuckDB) og SaaS (ClickHouse tar inn Parquet)

Bufringsstrategi

ArtefaktLagringTTL

AnalyseresultaterPostgres JSONBSesjonslevetid
TidsserieindeksObjektlagerSamme som Parquet
AI-svarPostgresUbegrenset (revisjon)

CREATE TABLE api_keys (
    id            uuid PRIMARY KEY,
    workspace_id  uuid REFERENCES workspaces NOT NULL,
    name          text NOT NULL,            -- "Enonic XP production"
    key_hash      text NOT NULL,            -- bcrypt hash of the key
    key_prefix    text NOT NULL,            -- "lp_live_a3f2..." (first 8 chars, for display)
    scopes        text[] NOT NULL,          -- {"ingest", "read", "analyze", "admin"}
    expires_at    timestamptz,              -- optional expiry
    created_by    uuid REFERENCES users,
    created_at    timestamptz DEFAULT NOW(),
    last_used_at  timestamptz
);

-- Key format: lp_live_a3f2b8c1d9e0f7... (easy to identify as LogPilot key)

10. Fremtidig: Kildekodeoppslag

Dette er IKKE Sentry

LogPilot instrumenterer ikke applikasjonen din. Ingen SDK, ingen agent, ingen kjøretidstilgang. I stedet, når LogPilot finner en stacktrace i loggene dine, kan den valgfritt slå opp den tilsvarende kildekoden i et tilkoblet Git-repo — noe som gir AI mer kontekst for å forklare feilen. Dette er et etterfølgende undersøkelsesverktøy, ikke sanntids feilsporing.

Ideen

LogPilot trekker allerede ut unntak og stacktraces fra logger. I dag forklarer AI dem basert på loggkonteksten alene. Med en valgfri Git-repo-tilkobling kan LogPilot også vise hvilken kode stacktracen peker til — og beriker undersøkelsen uten å kreve noen endringer i kundens applikasjon.

What LogPilot already does What source lookup adds (optional) ┌─────────────────────────┐ ┌────────────────────────────────┐ │ Parses logs │ │ Resolves stacktrace frames │ │ Detects incidents │ + │ to actual source files + lines │ │ Finds root causes │ │ Shows surrounding code │ │ AI explains from log data │ │ AI explains from log + code │ └─────────────────────────┘ └────────────────────────────────┘ works without repo requires optional repo connection

Slik fungerer det

  1. Workspace-admin kobler til et repo (valgfritt, én gang). Skrivebeskyttet tilgang via GitHub App, deploy-nøkkel, PAT eller lokal sti.
  2. LogPilot indekserer symboler i bakgrunnen: bygger en oppslagstabell over pakke.klasse.metode → fil:linje. Dette er en lettvekts symboltabell, ikke en full kopi av koden.
  3. Når en stacktrace dukker opp i en hendelse, løser LogPilot rammer mot symboltabellen: com.enonic.xp.repo.BlobStore.get() → src/repo/BlobStore.java:142.
  4. AI-kontekstbyggeren inkluderer de løste kildelinjene (20 linjer rundt rammen) ved siden av de eksisterende hendelsesdataene. AI kan nå forklare feilen i form av faktisk kode.

Hva brukeren ser

Uten kildekodeoppslag (standard)Med kildekodeoppslag (repo tilkoblet)
Hendelse: Database Connection Cascade
Årsak: NullPointerException i BlobStore.get()
Bevis: 47 forekomster, 3 systemer berørt
AI sier: “Blob store-oppslaget feiler når cache-nøkkelen er null, sannsynligvis under en indeksgjenoppbygging…” 		Hendelse: Database Connection Cascade
Årsak: NullPointerException i BlobStore.get()
Kilde: src/repo/BlobStore.java:142
Kode: blob = cache.get(key);
Sist endret: 15. feb av dev@enonic.com
AI sier: “Linje 142 sender key til cache.get() uten null-sjekk. key blir null når RepoIndex.rebuild() (linje 89) kjøres under en klusterdeling. Løsning: legg til if (key == null) return Optional.empty(); før cache-oppslaget.”

Produktet fungerer fullt ut uten en repo-tilkobling. Kildekodeoppslag er en “koble til repoen din for dypere innsikt”-funksjon, ikke et krav.

Arkitektur (lettvekts)

KomponentHva det gjør
Git-kobling Skrivebeskyttet grunn kloning eller lokal sti-montering. Henter inkrementelt (ved webhook eller tidsplan). Skriver aldri til repoen.
Symbolindekserer Analyserer kildefiler, bygger klasse.metode → fil:linje-oppslag. Lagret i Postgres per workspace. Liten: ~1 MB per 100K LOC-repo.
Rammeløser Tilordner stacktrace-rammer fra logg-hendelser til kildelokasjoner ved hjelp av symbolindeksen. Rask minnebasert oppslag.
Kontekstberiker Leser ~20 linjer kilde rundt løste lokasjoner. Legger til git blame (hvem, når). Mates inn i eksisterende AI-kontekstbygger.

Tilkoblingsalternativer

MetodeBest for
GitHub AppSaaS-kunder på GitHub — ett-klikks installasjon

Deploy-nøkkel (SSH, skrivebeskyttet)Alle Git-verter, selvhostet Git

Språkstøtte

SpråkHvordan stacktrace → kilde fungerer

Sikkerhet

  • Skrivebeskyttet: LogPilot skriver aldri til repoen. Ingen push-tilgang, ingen PRer, ingen endringer.
  • Workspace-avgrenset: Repo-tilkobling og symbolindeks tilhører workspacet. RLS gjelder. Andre workspaces kan ikke se koden.
  • Redigering gjelder: Kildekode sendt til AI passerer gjennom samme RedactionGate. Hardkodede hemmeligheter i kode blir redigert.
  • Minimale data: LogPilot lagrer en symbolindeks (~1 MB), ikke en full kodekopi. Kildelinjer hentes ved behov for løste rammer.
Byggeprioritet: V2+

Kjerneprodukte — loggparsing, heuristikk, hendelsesdeteksjon, AI-forklaring — må fungere utmerket uten noen repo-tilkobling. Kildekodeoppslag er et berikningslag som gjør AI smartere når det er tilgjengelig. Arkitektonisk er det et nytt adapter (Git-kobling) og en ekstra inngang til den eksisterende AI-kontekstbyggeren — ingen endringer i kjerne-analysepipelinen.
